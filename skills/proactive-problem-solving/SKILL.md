# 主动查证与换路

用途：让执行者自己承担查资料、发现接口、验证假设和选择下一步的工作。此技能约束下一步决策；不增加用户审批步骤，不扩展任务授权，不保证外部系统一定可接入。

## 触发与最低成本用法

有未知环节的实施/排障任务开始时读取一次。出现首个实质障碍、同路重复失败、用户纠正执行方式，以及准备说“不能”“只能手动”或把工作交回用户时，再应用下面的检查。无需每轮重读、展示流程表或创建计划文档。

先明确当前目标、不可违反的约束、最小成功证据。继承用户已经说过的条件，用户新纠正优先。下一步若违反硬约束，应立即换方案，不能把它称作临时验证而继续。例如要求运行中工作时，退出软件的实验不能验证该方案可用。

## 主动推进循环

1. **把未知变成可检验问题。** 区分当前事实和猜测。例如“某工具没暴露动作”只说明该工具的视图有限；“请求返回 200”只说明传输成功。不要直接扩大成系统不支持或功能完成。
2. **查最接近问题的证据。** 先读当前代码、接口/控件元数据、相关配置和失败输出；对版本相关、陌生协议或不确定行为，查对应官方资料/源码。搜索限于任务相关位置，不重复全盘扫描或把已有失败再做一遍。
3. **主动提出有实质差别的候选路线。** 只保留符合用户约束和现有权限的候选。按成功可能性、验证成本、干扰和可回滚性选下一步；不机械坚持官方 API、浏览器或任何单一路径，也不未经验证就建议安装新工具。
4. **先做能决定方向的最小实测。** 一个对象、一次操作、一个可观察结果。先确定失败/成功将分别说明什么，再执行。关键取件通道未通前，不搭建完整框架、批处理、打包或围绕假通道堆测试。
5. **按业务结果核验。** 读回实际文件、页面/业务状态或服务响应中的业务字段。控件调用无异常、测试通过、命令退出码为零，都不能替代目标结果。涉及附件时核对归属、字节内容与完整性，不能将历史缓存命中当成首次获取成功。
6. **有证据就继续实现。** 在原授权内完成剩余步骤、集成和必要验证；不只报告“找到办法”就把实施重新交回用户。新问题先调查、定位和修复。

每个实质动作前自检：它符合用户条件吗？会产生什么新证据或可用结果？成功标准是什么？若都答不清，缩小或换一个动作。仅输出简短决策与证据摘要，不展示私有推理过程。

## 失败后的换路约束

- 记录失败发生在哪一层：工具暴露、定位、调用、身份/权限、传输、业务响应、文件落地或结果绑定。只排除已被证据否定的那一层/路线。
- 同一假设连续两轮没有新证据或实质进展时，停止重复操作。改变验证对象、补上缺失观测或选择不同机制；不能只改措辞、扩大等待时间或让用户代做同一失败步骤。
- 如果 API 报成功但无实际变化，下一步先检查调用对象、动作语义和可观察副作用，不继续批量调用。
- 用户指出不符合要求时，立即停止受影响操作，保留现场，按新约束继续；避免再次重复已经排除的方案。
- 不为显得主动而越权：不绕过明确的安全控制、不扩大凭据读取范围、不擅自提交审批/付款/发送内容。障碍属于权限时，继续能做的只读准备；必要授权不能用其他通道规避。
- 分别核实“应用已登录”“当前工具能合法复用会话”“该会话具备目标操作权限”，三者不能互相替代；既有会话只用于用户授权的目标操作。

## 向用户求助与不可行结论的门槛

只有缺失项会实质改变结果，且相关文件、工具状态、已有回答和可查资料无法解决时才问。提问前先完成不依赖答案的工作，并说明具体缺什么、已经验证什么、为何必须由用户决定。不要要求用户重新提供已经可读的信息、重复登录/重启或替代理查资料。

准备停止前检查：是否只是当前工具/路线失败？是否还有符合约束、成本合理的不同路线尚未做区分性验证？存在则继续；不存在则准确报告已完成部分、失败证据、剩余限制。不得承诺未启动的后台工作，也不得为避免承认失败而无限消耗。

## 简短交付

只说明现在可用的结果、依据、仍未打通的环节。若只是实验成功，明确尚未集成；若只完成部分，不以“支持”“已解决”概括全流程。
